How a language model is built · three phases

Library, School, Apprenticeship

A model is trained three times, on the same weights. Each phase installs something different — and only the last one decides what the model actually does. Every diagram below shows a mechanism; every phase comes with a real training sample.

The anchor picture

One set of weights, edited three times

The thick horizontal line is the model's weights. Data pours in from above — and the pipe gets dramatically thinner at every stage. What comes out the bottom of each station is a model you could, in principle, ship.

Phase 01 · the library

Pre-training: predict the next token, ten trillion times

No labels, no questions, no answers. Just text with the next word hidden — over and over, until the weights encode how language, code and the world tend to continue.

Pre-training samplesupervision signal: the next token, nothing else
… because the interlocking must never grant two conflicting routes at
once, the controller checks the switch position before it clears the
signal. In practice this means …

# and, from a completely different file in the same shuffled batch:
def clamp(x, lo, hi):
    return max(lo, min(x, hi))
Two unrelated fragments, no instruction anywhere, no notion of a “user”. The base model that comes out of this phase does not answer questions — it continues text. Ask it “What is a clamp?” and it may happily reply with “What is a switch? What is a route?”, because a list of questions is a plausible continuation.

Phase 02 · the school

Mid-training: same lesson, different diet

Nothing changes about how the model learns here. What changes is which documents are in the bucket — and that quietly decides what the finished model will be good at.

Mid-training samplesupervision signal: still just the next token
# one sample = one whole repository, concatenated in dependency order
repo/README.md            60 lines
repo/src/clamp.py          8 lines
repo/tests/test_clamp.py  24 lines
repo/CHANGELOG.md        140 lines
—— 18,400 tokens, fed as a single unbroken sequence ——
Feeding a repository whole (instead of a random 4,000-token slice of one file) is what teaches the model that a test file and an implementation file are related — and to hold both in mind at once. Same objective as phase 1; a deliberately different bucket.

Phase 03 · the apprenticeship

Post-training: where behaviour is installed

Three sub-stages, run in order, each consuming a different kind of supervision. This is the phase that turns “text continuer” into “assistant that finishes a task” — and the phase behind almost every headline benchmark jump on agentic work.

Four acronyms show up here, so spelled out once: SFT is supervised fine-tuning, RLHF is reinforcement learning from human feedback, DPO is direct preference optimisation, and RLVR is reinforcement learning from verifiable rewards.

01 · SFT samplesupervision signal: imitate this exact answer
{
  "prompt":   "The test in tests/test_clamp.py fails. Fix it.",
  "response": "I'll read the test before changing anything.\n
               <read tests/test_clamp.py>\n
               The test calls clamp(5, 10, 0) and expects a ValueError,
               so the bounds need validating. Editing src/clamp.py:\n
               <edit src/clamp.py>\n
               <run pytest -q>  → 3 passed\n
               Fixed: clamp now rejects lo > hi."
}
Notice what is really being taught: not the fix, but the habit — read before editing, run the tests afterwards, report what happened. A few hundred thousand demonstrations like this is what makes a model behave like an assistant instead of continuing your prompt.
02 · Preference samplesupervision signal: relative — B is worse than A
{
  "prompt":   "Why does clamp(5, 10, 0) return 0?",
  "chosen":   "Because lo=10 and hi=0 are swapped. min(5, 0) is 0, and
                max(10, 0) is 10 … so the bound check happens in the
                wrong order. Validate lo <= hi first.",
  "rejected": "Great question! Clamping is a very common operation in
                programming. Let me explain what clamping means …"
}
Nobody had to write the perfect answer here — only to say which of two real outputs was better. That is far cheaper to collect at scale, and it is where “gets to the point”, “doesn't flatter you” and “admits uncertainty” actually come from.

Stage 3 is the one worth understanding properly, because it works differently from the other two: the model is not shown a target at all. It is turned loose on a real task, many times, and the environment itself decides which attempts get reinforced.

03 · RLVR samplesupervision signal: did the whole trajectory work?
task:       make `pytest tests/test_clamp.py` exit 0

attempt 7:  <edit src/clamp.py> → <run pytest> → 2 failed       reward 0
attempt 8:  <read tests/test_clamp.py> → <edit src/clamp.py>
            → <run pytest> → 3 passed                        reward 1

update:     every token of attempt 8 — including the decision to read
            the test first — becomes more likely next time.
            every token of attempt 7 becomes less likely.
This is the mechanism behind “the model learned to plan”. Nobody wrote a rule saying read before editing. The attempts that read first passed more often, so reading first got reinforced. Multiply by millions of tasks and you get an agent that behaves methodically.

The case that makes the point

GLM-5.3: a capability jump with no new base model

On 14 August 2026, Z.ai shipped GLM-5.3 on the same 743-billion-parameter base as GLM-5.2. Everything left of the last box was reused bit for bit; only post-training was scaled up.

Post-training is cheap relative to pre-training, so a lab holding a good base model can ship capability jumps repeatedly without paying for another base run. Expect the release cadence to keep looking like this.

Keeping it honest

What post-training can and cannot do

Can

  • Make capability the base already has reliably reachable — the difference between knowing every shell command and finishing a shell task.
  • Install habits: plan first, verify after, stop when done, ask when blocked.
  • Extend the horizon — from one good answer to a hundred coherent steps.
  • Shape tone, refusals, formatting, tool-calling syntax.

Cannot

  • Add knowledge the base never saw. No amount of post-training teaches a fact absent from pre-training.
  • Change architecture-level limits — tokenizer, context length, parameter count.
  • Guarantee the gain generalises. Training against graders can also teach the model to fit the grader, and benchmark-shaped tasks are the easiest thing to overfit.
  • Prove anything about safety. A model can be simultaneously more capable at security tasks and less predictable — which is the stated reason GLM-5.3's weights were held back.

That last column is why “gains came purely from post-training” is an interesting claim rather than a settled one. It is fully consistent with a real jump in competence, and equally consistent with a recipe tuned closely to the benchmarks it reports. Open weights are what lets someone else tell the difference.

If you keep three sentences

Pre-training decides what the model knows. Mid-training decides what it is good at. Post-training decides what it does — and it is the only one of the three you can redo cheaply, which is why it is where the competition now happens.
